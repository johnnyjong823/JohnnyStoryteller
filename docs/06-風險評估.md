## 風險 1：網站容量撞到 1 GB 硬限制

**機率：確定會發生**（你已經說了目標 300 篇以上）
**衝擊：高**（超過後網站發布會失敗，不是變慢而是整個掛掉）

### 容量試算

假設每篇 12 場景 + 1 封面 = **13 張圖**。

單張圖的輸出變體（扁平插畫風、AVIF 品質約 50）：

| 變體 | 用途 | 估計大小 |
|---|---|---|
| AVIF 480w | 手機 | ~25 KB |
| AVIF 960w | 平板 | ~70 KB |
| AVIF 1440w | 平板 Retina | ~130 KB |
| WebP 960w | 舊瀏覽器備援 | ~130 KB |
| **合計** | | **~355 KB** |

**每篇 = 13 × 355 KB ≈ 4.6 MB**

### 撞牆時間表

| 故事數 | 網站容量 | 狀態 |
|---|---|---|
| 50 | 230 MB | 🟢 完全沒問題 |
| 120 | 550 MB | 🟢 |
| 180 | 830 MB | 🟡 **開始準備** |
| **200** | **920 MB** | 🔴 **必須動作** |
| 300 | 1.4 GB | ❌ **超出，網站發布失敗** |

### 三段警戒線

```
🟢 0–120 篇    什麼都不用做
🟡 120 篇      建 Cloudflare 帳號與 R2 bucket，做一次遷移演練
🔴 180 篇      執行遷移（不要等到 200，留緩衝）
```

**檢查方式**：每次建置後看 `dist/` 的大小

```bash
du -sh dist/
```

超過 **700 MB** 就開始準備。

### 緩解：`assetUrl()` 抽象（已寫進架構）

架構上從第一天就把圖片路徑抽成一支函式（[見 02](./02-技術架構.md#-核心決定asseturl-圖片路徑抽象)）。現在它什麼都沒做，但它讓「搬家」從**重寫程式碼**變成**改一個環境變數**。

### 遷移劇本（約半天）

1. 建 Cloudflare R2 bucket，綁自訂網域 `img.你的網域.com`
2. `rclone sync` 把圖片同步上去
3. GitHub repo → Settings → Secrets and variables → Actions → 加變數 `PUBLIC_ASSET_BASE_URL=https://img.你的網域.com`
4. 建置腳本改成不輸出圖片到 `dist/`
5. push，驗證

**內容 Markdown 一個字都不用改。**

### 成本

Cloudflare R2 免費額度：**10 GB 儲存 + egress 完全免費**。

300 篇 = 1.4 GB，遠低於免費額度 → **$0**。就算長到 2000 篇（約 9 GB）也還在免費額度內。

### ⚠ 為什麼不用 Cloudflare Pages 放圖片

CF Pages 免費版有 **20,000 檔上限**（來源：<https://developers.cloudflare.com/pages/platform/limits/>）。

300 篇 × 13 圖 × 4 變體 = **15,600 個圖片檔**，加上 HTML/JS/CSS 會逼近 20,000。太貼邊。

**R2 沒有檔案數量限制** — 圖片要放 R2，不是 CF Pages。

## 風險 2：repo 容量與 git 歷史膨脹

**機率：高** ｜ **衝擊：中**（不會立刻壞，但會越來越慢、越來越難處理）

GitHub 對來源 repo 的**建議**上限也是 1 GB。master 圖每張約 250 KB：

> 300 篇 × 13 張 × 250 KB ≈ **975 MB** — 剛好卡在建議上限

### 更麻煩的是：git 歷史刪不掉

你重畫一張圖 commit 上去，**舊的那張永遠留在歷史裡**。同一張圖改 20 次 = 20 份都在 repo 裡，`git clone` 每次都要下載。

刪掉檔案不會縮小 repo — 只有改寫整個歷史（`filter-repo`）才行，而那會破壞所有既有的 clone。

### 緩解

| 做法 | 說明 |
|---|---|
| **壓好再 commit** | 不要先傳原始 PNG／4K 圖再壓縮。原始大檔一律留在本機，不進版控 |
| **一次 commit** | 一篇故事的圖全部確認 OK 再一起 commit，不要邊改邊 commit |
| **不要用 Git LFS** | ⚠ **GitHub Pages 不提供 LFS 檔案服務**，會直接吐出 LFS 指標文字檔，圖片全壞 |
| **重畫用新檔名** | 真的要改某一張，考慮用 `03b.webp` 而不是覆蓋 `03.webp`（雖然會留下無用檔案，但至少歷史裡只有一份） |

### 觸發門檻

```bash
git count-objects -vH     # 看 size-pack
```

超過 **700 MB** → 考慮讓圖片以 R2 為單一來源，repo 只留 Markdown。這跟風險 1 的遷移是同一件事，一起做。

## 風險 3：公開 repo 的內容隱私（已決定接受）

> ✅ **2026-08-18 決定：走公開 repo + 免費 GitHub Pages。** 這一節保留下來，是為了記錄「接受了什麼」以及「什麼時候該回頭重新考慮」。

**機率：確定** ｜ **衝擊：視內容而定** ｜ **狀態：已知並接受**

免費方案的 GitHub Pages 只能用在**公開 repo**。所以現在起：

- 所有故事文字與圖片，**全世界都看得到**
- Google 等搜尋引擎會索引
- 任何人都能 clone 整個 repo，包含 git 歷史

### 這代表寫故事時要注意

因為決定公開了，內容上就有一條紀律：

| 不要放進故事 | 替代做法 |
|---|---|
| 孩子的真實姓名 | 換個名字，或用暱稱 |
| 可辨識的地點（學校名、社區名、門牌） | 寫成「他的學校」「巷子口」 |
| 孩子的真實照片 | 一律用 AI 插畫（本來就是這樣做） |
| 具體的家庭事件細節 | 抽象化成故事情節 |

**故事的情感是真的，細節不用是真的。** 這條紀律的成本很低，但一旦漏了就撤不回來 —— git 歷史刪不掉（見[風險 2](#風險-2repo-容量與-git-歷史膨脹)）。

### 什麼時候該回頭重新考慮

如果哪天出現以下情況，隨時可以改走私有：

| 選項 | 費用 | 說明 |
|---|---|---|
| **GitHub Pro** | 約 $4/月 | 私有 repo 也能用 Pages |
| **Cloudflare Pages** | **$0** | **免費就能從私有 repo 建置**。網站公開但原始碼私有，流量也不限 |

**切換成本接近零** —— Astro 的輸出是與主機無關的純靜態檔，換主機只是換部署設定，內容與程式碼完全不用改。這正是[風險 9（供應商鎖定）](#風險-9供應商鎖定)那條紀律的價值所在。

### 部分緩解（不是隱私保護）

`robots.txt` + `<meta name="robots" content="noindex">` 可以避免被搜尋引擎索引。**但 repo 本身還是公開的**，任何人知道網址就能看。這只是降低曝光，不是保護 —— 真正的防線是上面那張「不要放進故事」的表。

## 風險 4：流量軟限制 100 GB/月

**機率：低** ｜ **衝擊：中**（超過會被 GitHub 聯絡，極端情況停用）

### 實際換算

一次故事瀏覽只會下載該裝置尺寸的 AVIF：

| 裝置 | 每次瀏覽 |
|---|---|
| 平板（960w） | 13 × 70 KB ≈ **0.9 MB** |
| 手機（480w） | 13 × 25 KB ≈ **0.33 MB** |

> 100 GB ÷ 0.9 MB ≈ **每月 11 萬次故事瀏覽**

個人與家庭使用完全不會碰到。只有網站變成熱門公開資源才需要擔心 — 而那時風險 1 的 R2 遷移同時就解決了（**R2 egress 免費**）。

## 風險 5：內容治理 —「越來越雜」

**機率：高**（你自己指出的） ｜ **衝擊：高**（篩選功能會直接失效）

這是最容易在 **100 篇之後**爆掉的風險，而且**不能靠自律解決** — 你寫第 87 篇的時候不會記得第 12 篇用了哪個詞。

| 失控形式 | 後果 | 防線 |
|---|---|---|
| 標籤同義詞爆炸（勇敢/勇氣/有勇氣/不怕） | 篩「勇敢」只篩到五分之一 → 篩選功能廢掉 | `taxonomy.ts` 白名單 + zod 驗證，**build 失敗** |
| 分類過多過細 | 選單一排 30 個 chip = 等於沒分類 | **上限 12 個**，寫進文件 |
| slug 命名不一致（中文/大寫/底線混用） | 網址醜、難分享、工具出錯 | 命名規則 + build 驗證 |
| 場景數量差太多（3 張 vs 40 張） | 播放體驗不一致 | schema 限制 **8–16 張** |
| 缺 `alt`、缺 `quiz` | 無障礙破損、故事沒結尾 | schema 設為必填 |
| `summary` 寫太短或沒寫 | **搜尋找不到** | schema 限制 20–80 字 |

### ★ 核心觀念

> **讓錯誤在 build 時就爆炸，而不是在你說故事給孩子聽的時候才發現。**

打錯一個標籤 → `npm run build` 失敗，訊息直接告訴你哪一篇、哪一行、正確的選項有哪些。這比任何規範文件都有效。

## 風險 6：建置時間隨故事數線性成長

**機率：確定** ｜ **衝擊：低到中**（不會壞，但會煩）

sharp 圖片轉檔是建置最花時間的部分：

> 300 篇 × 13 張 × 4 個變體 = **15,600 次轉檔**

冷啟動可能要 **20–40 分鐘**。每次改一個錯字都要等這麼久，會直接讓你不想更新網站。

### 緩解

1. **把 Astro 的圖片快取目錄納入 GitHub Actions cache** → 只有新增/修改的圖會重轉，其餘直接命中快取
2. 觸發門檻：**單次建置超過 10 分鐘** → 檢查快取有沒有生效
3. 終極解法：圖片轉檔搬到本機或獨立步驟，只把成品推上去 — 這跟風險 1 的 R2 遷移是同一件事

## 風險 7：離線與弱網路

**機率：中高** ｜ **衝擊：高**（體驗直接毀掉）

情境：車上、外出、家裡 wifi 不穩。故事說到第 5 頁，圖片載不出來 — 孩子的注意力當場斷掉，而且很難救回來。

### 緩解

PWA + 「離線收藏」按鈕（[路線圖階段 4](./07-實作路線圖.md#階段-4pwa-離線)）。

⚠ **絕對不要全站預快取** — 300 篇 = 1.4 GB 塞進使用者手機會直接失敗，還會吃掉行動數據。策略見 [02](./02-技術架構.md#pwa-離線策略)。

## 風險 8：兒童隱私

**機率：低**（只要不主動加東西） ｜ **衝擊：高**（法律風險）

只要網站公開且面向兒童，COPPA / GDPR-K 就是真實存在的，不是假想的。

### 緩解（全部已寫進設計）

- **不放任何追蹤分析**（GA、FB Pixel 等）
- **問答不計分、不記錄、不上傳**
- 所有狀態（看過的故事、進度、字級偏好）**只存 localStorage**
- 之後若想看流量，用 cookieless 的自架方案，且不記錄任何可識別資訊

## 風險 9：供應商鎖定

**機率：低** ｜ **衝擊：低**（只要保持紀律）

### 原則

> `dist/` 必須是與主機無關的純靜態檔。

- 不使用 GitHub Pages 專屬功能
- **不使用 Cloudflare Workers / Netlify Functions 這類綁定平台的東西**
- 隨時可以搬到 Cloudflare Pages / Netlify / Vercel / 自己的 VPS

這條紀律的價值在風險 3 就會兌現 — 如果決定改用 Cloudflare Pages，成本接近零。

## 風險 10：`base` 路徑設定錯誤

**機率：高**（因為[決定不綁自訂網域](#-2-暫不綁自訂網域)） ｜ **衝擊：中** ｜ **必須在階段 1 處理**

⬆ 這項風險因為 2026-08-18 的決策而**升級**。原本綁自訂網域就能完全繞過，現在必須正面處理。

專案頁的網址是 `你的帳號.github.io/repo名稱/`。如果程式碼裡寫死 `/stories/...`，會出現：

> **本機開發完全正常，線上全部 404** — 而且很難 debug

會踩到的地方比想像中多：CSS 背景圖、`<a href>`、`fetch()` 搜尋索引、PWA manifest 的 `start_url`、Service Worker 的 scope。

### 緩解

- `astro.config.mjs` 設 `base: '/<repo名稱>'`
- **所有站內連結一律用 `import.meta.env.BASE_URL` 開頭，禁止寫死開頭的 `/`**
- **所有圖片一律走 `assetUrl()`**（[見 02](./02-技術架構.md#-核心決定asseturl-圖片路徑抽象)）——
  它本來是為了日後搬 R2 而設計的，順便也解決了 base 路徑
- **階段 1 的驗收就包含這一項**：部署到線上後用手機實際開一次，確認圖片與連結都正常（本機測不出這個問題）

### 日後綁網域時

拿掉 `astro.config.mjs` 的 `base` 一行 + 設 DNS。因為連結與圖片都走抽象層，**程式碼不用動**。

### ✅ 4. 故事文字用 Manus 產生

**連帶動作**：這讓[風險 5（內容治理）](#風險-5內容治理-越來越雜)的重要性明顯上升。人類作者會記得規則，LLM 每次都會重新發明標籤、把 `alt` 寫成 `caption` 的複製、把 0-based 索引寫成 1-based。

`src/content.config.ts` 的 zod schema 因此從「文件規範」升級成**唯一的品質防線**。提示詞範本與七個陷阱見 [08](./08-用-Manus-產生故事.md)。
