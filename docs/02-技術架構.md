# 02 — 技術架構

## 選型結論

**Astro（`output: 'static'`）+ TypeScript + Content Collections + GitHub Actions → GitHub Pages**

### 為什麼是 Astro

| 專案需求 | Astro 怎麼滿足 |
|---|---|
| 純靜態、要能放 GitHub Pages | `output: 'static'` 產出純 HTML/CSS/JS，Pages 只負責發送檔案 |
| 300+ 篇故事，內容必須有結構 | Content Collections + zod schema，欄位打錯 build 直接失敗 |
| 圖片必須自動壓縮才不會撞 1 GB | 內建 `<Image>` / `<Picture>`（底層 sharp），自動產 AVIF/WebP 多尺寸 |
| 每篇故事要能單獨分享連結 | 每篇輸出獨立 HTML，不是 SPA — 不需要 404 fallback、不需要 hash routing |
| 孩子的裝置不要跑一堆 JS | 預設零 JS。只有播放器與問答這兩個「島」才載入 JS |
| 之後可能要搬家 | `dist/` 是與主機無關的純靜態檔 |

### Astro 放 GitHub Pages 完全沒問題

`output: 'static'` 的輸出對 Pages 來說，跟手寫 HTML 沒有任何差別。而且官方文件明載：

> GitHub Pages sites have a *soft* limit of 10 builds per hour. **This limit does not apply if you build and publish your site with a custom GitHub Actions workflow.**

所以走 Astro + Actions 反而比傳統 Jekyll 模式**更沒有限制**。

## 部署管線

### `astro.config.mjs` 關鍵設定

```js
import { defineConfig } from 'astro/config';

export default defineConfig({
  site: 'https://<你的帳號>.github.io',
  base: '/<repo名稱>',      // ⚠ 專案頁必須設；user page 或自訂網域則整行拿掉
  output: 'static',
  image: {
    // 只產真正會用到的尺寸，多產一個尺寸 = 多佔 1/4 的容量
    // 見 04-圖片製作指南
  },
});
```

### GitHub Actions workflow

用官方的 `withastro/action` + `actions/deploy-pages`，加上兩層快取：

- `node_modules` 快取 — 加快安裝
- **Astro 圖片轉檔快取** — 這是 300 篇時的關鍵，沒有它每次 push 都要重轉 15,600 張圖（見風險 6）

Repo 設定：Settings → Pages → Source 選 **GitHub Actions**（不是 "Deploy from a branch"）。

## ★★ 核心決定：`assetUrl()` 圖片路徑抽象

### 為什麼現在就要做

300 篇會超過 GitHub Pages 的 1 GB 硬限制（[詳見 06](./06-風險評估.md#風險-1網站容量撞到-1-gb-硬限制)）。但現在就搬到外部 CDN 是過度設計 — 前 120 篇完全不需要。

所以目標是：**讓「搬家」變成改一個環境變數的事，而不是重寫程式碼的事。**

### 實作

```ts
// src/lib/assetUrl.ts
const EXTERNAL = import.meta.env.PUBLIC_ASSET_BASE_URL ?? '';

/**
 * 產生故事圖片的 URL。
 * 未設定 PUBLIC_ASSET_BASE_URL 時走同源（GitHub Pages）；
 * 設定後自動改指向外部 CDN（Cloudflare R2），內容檔案完全不用改。
 */
export function assetUrl(storySlug: string, file: string): string {
  if (EXTERNAL) {
    return `${EXTERNAL.replace(/\/$/, '')}/stories/${storySlug}/${file}`;
  }
  return `${import.meta.env.BASE_URL}stories/${storySlug}/${file}`;
}
```

### 一條必須遵守的規則

> **任何地方都不准寫死圖片路徑，一律走 `assetUrl()`。**

這條規則現在看起來多餘 — 因為 `EXTERNAL` 永遠是空字串。但它是唯一讓你未來半天內完成搬家的東西。

同理，所有站內連結一律用 `import.meta.env.BASE_URL` 開頭，不要寫 `/stories/...`（見踩雷點 1）。

### 未來搬家時要做的事（半天）

1. 建 Cloudflare R2 bucket，綁自訂網域 `img.你的網域.com`
2. `rclone sync` 把圖片同步上去
3. GitHub repo → Settings → Secrets and variables → Actions → 加 `PUBLIC_ASSET_BASE_URL=https://img.你的網域.com`
4. 建置腳本改成不輸出圖片到 `dist/`
5. push

**內容 Markdown 一個字都不用改。**

## 搜尋方案

### 階段一：metadata 索引（現在 → 300 篇）

建置時由 `src/pages/search-index.json.ts` 產生一份 JSON，只含 metadata：

```
{ slug, title, summary, category, tags, ageRange, minutes, cover }
```

容量試算：
- 每篇約 200 bytes
- 300 篇 ≈ **70 KB**，gzip 後 ≈ **25 KB**

這個大小可以直接在瀏覽器一次載入、記憶體內比對，**快到不需要任何搜尋函式庫**。

### 階段二：Pagefind（如果要搜尋故事內文）

觸發條件：你開始出現「我記得有一篇裡面提到兔子，但標題沒有兔子」這種需求。

Pagefind 會把索引切塊、按需載入，而且原生支援 CJK 分詞，是靜態網站全文搜尋的標準解。到時候換掉即可，不影響其他部分。

### ⚠ 中文搜尋的坑

**不要直接用 Fuse.js / Lunr / MiniSearch 的預設設定。**

它們預設用空白斷詞。中文沒有空白，整句會被當成一個 token — 搜「小紅」找不到「小紅帽」，篩選功能等於失效。

正確做法：

```ts
// src/lib/search.ts 的核心思路
// 1. 正規化：轉小寫、全形轉半形、去標點、去空白
// 2. 子字串比對（indexOf）— 300 篇的規模這樣就夠快了
// 3. 若之後變慢，再加 bigram 倒排索引加速
```

300 篇 × 平均 100 字的可搜尋文字 = 3 萬字元。純 `indexOf` 掃過去在現代手機上是**毫秒等級**，不需要提前最佳化。

**加分項（後續選項）**：注音／拼音首字母比對 — 打「xhm」找到「小紅帽」。需要一張中文轉拼音對照表，不是 MVP 必要。

## PWA 離線策略

用 `@vite-pwa/astro`（Astro 的官方 PWA 整合）。

### ★ 一條鐵則

> **絕對不要預快取所有故事圖片。**

300 篇 = 1.4 GB。塞進使用者手機會直接失敗，而且會消耗掉他們的行動數據。

### 分層策略

| 層 | 內容 | 策略 |
|---|---|---|
| 殼層 | HTML、CSS、JS、字型 | **預快取**（precache）— 幾百 KB |
| 索引 | `search-index.json` | 預快取 + 背景更新 |
| 封面縮圖 | 320px 封面 | Runtime 快取，用過就留（300 張 × 15 KB ≈ 4.5 MB，可接受） |
| **故事圖片** | 場景大圖 | **只在使用者按「離線收藏」時才下載** |

### 離線收藏 UI

- 故事頁有一個「離線收藏」按鈕 → 下載該篇全部圖片進 Cache Storage
- `/offline` 頁面列出已收藏的故事，可以刪除、顯示佔用空間
- 選單上已收藏的故事有標記

## 已知踩雷點清單

### 1. `base` 路徑（最容易出事）

專案頁的網址是 `你的帳號.github.io/repo名稱/`。如果 `astro.config.mjs` 沒設 `base`，或程式碼裡寫死了 `/stories/...`，會出現：**本機開發完全正常，線上全部 404**。而且很難 debug。

緩解：
- 一律用 `import.meta.env.BASE_URL` 組連結
- **最好的解法：綁自訂網域，或用 user page（`你的帳號.github.io`）**，就完全不需要 `base`

### 2. `.nojekyll`

Astro 會輸出 `_astro/` 目錄。Jekyll 會忽略所有底線開頭的目錄 → CSS/JS 全部 404。

用官方 Actions 部署時通常已經處理好，但在 `public/.nojekyll` 放一個空檔是零成本保險。**放就對了。**

### 3. Git LFS 的檔案 GitHub Pages 不會提供服務

如果為了省 repo 空間把圖片放進 Git LFS，Pages 會直接吐出 LFS 指標文字檔，圖片全部壞掉。

**結論：圖片絕對不能用 LFS。** 想省空間只能靠壓縮或外部託管（R2）。

### 4. 建置次數限制

走自訂 Actions workflow 就沒有每小時 10 次的軟限制。不用擔心。

### 5. 建置時間會隨故事數線性成長

300 篇 × 13 張圖 × 4 個輸出變體 = **15,600 次 sharp 轉檔**。冷啟動可能要 20–40 分鐘。

緩解：把 Astro 的圖片快取目錄納入 Actions cache，只有新增/修改的圖會重轉。
觸發門檻：單次建置超過 10 分鐘 → 檢查快取有沒有生效。詳見 [06 風險 6](./06-風險評估.md#風險-6建置時間隨故事數線性成長)。

### 6. `100vh` 在 iOS Safari 會跳動

用 `100dvh`。這在播放器全螢幕版型上是必然會踩到的。完整清單見 [05 的 iOS 踩雷清單](./05-畫面與互動設計.md#-ios-踩雷清單)。

## 技術決策紀錄（為什麼不選其他方案）

| 方案 | 為什麼不選 |
|---|---|
| **零建置純手寫 HTML/JS** | 300 篇時，手動壓縮圖片與維護索引會變成全職工作。圖片自動最佳化是能不能撐過 1 GB 的關鍵 |
| **Next.js static export** | 對純靜態內容站太重，預設帶進大量 JS runtime，違背「孩子的裝置不要跑一堆 JS」 |
| **Eleventy** | 很好的選擇，但圖片最佳化與型別化內容 schema 要自己接。Astro 這兩件事是內建的 |
| **SPA + hash routing** | 每篇故事就是一個獨立頁面，靜態產生比 SPA 簡單也更快。SPA 只會帶來 404 fallback 這類額外複雜度 |
| **Git LFS 存圖片** | GitHub Pages 不提供 LFS 檔案服務（見踩雷點 3） |
| **Cloudflare Pages 存圖片** | 免費版 20,000 檔上限，300 篇會產生約 15,600 個圖片檔，太貼邊。要用 **R2**（無檔案數限制） |
