# 說書人強尼 — 規劃文件

一個給說書人用的兒童故事網站。進入是故事選單，選一篇後像投影片一樣一頁一頁播放（**大圖給孩子看、小字給說書人看**），說完接 2 題小題目。

## 一頁摘要

### 已確認的決策

| 項目 | 決定 | 理由 |
|---|---|---|
| 部署 | GitHub Pages（初期） | 免費、簡單、你已經在用 GitHub |
| 框架 | **Astro**（`output: 'static'`） | 純靜態輸出、內容有 schema、圖片自動最佳化、預設零 JS |
| 建置 | GitHub Actions | 官方文件明載：走自訂 Actions workflow 可**免除**每小時 10 次建置的限制 |
| 播放裝置 | **平板手持 + 手機** | 沒有投影機情境 → 觸控優先、深色介面、離線很重要 |
| 預期規模 | **300 篇以上** | 這個數字直接決定了整個架構，見下 |
| **repo 可見性** | **公開** ✅ | 接受故事內容公開，換取免費的 GitHub Pages |
| **自訂網域** | **暫不綁定** ✅ | 未來需要時再加。⚠ 代價：`base` 路徑必須正確處理 |
| **故事文字** | **Manus 產生** | 餵 schema 給 AI，見 [08-用-Manus-產生故事](./08-用-Manus-產生故事.md) |
| **場景插畫** | AI 繪圖（先 Gemini 驗證流程，衝量再上 Midjourney） | lovart.ai 免費額度不足，見 [04](./04-圖片製作指南.md#繪圖工具選擇) |

### 三件必須現在就處理的事

**1️⃣ 300 篇會超過 GitHub Pages 的 1 GB 硬限制**

每篇約 4.6 MB → **約 200 篇就會撞牆**。所以架構上從第一行程式碼就把圖片路徑抽成 `assetUrl()`，日後只要改一個環境變數就能把圖片搬到 Cloudflare R2（egress 免費、免費額度 10 GB），內容檔案一個字都不用改。
→ 詳見 [06-風險評估](./06-風險評估.md#風險-1網站容量撞到-1-gb-硬限制)

**2️⃣ 沒有自訂網域 → `base` 路徑一定要處理對**

網址會是 `<你的帳號>.github.io/<repo名稱>/`。只要程式碼裡寫死開頭的 `/`，就會出現「**本機開發完全正常、線上全部 404**」，而且很難 debug。

規則：`astro.config.mjs` 設 `base`，所有連結一律用 `import.meta.env.BASE_URL` 開頭，所有圖片一律走 `assetUrl()`。
→ 詳見 [06-風險評估](./06-風險評估.md#風險-10base-路徑設定錯誤)

**3️⃣ 「故事很雜」要靠 build 時驗證來解決，不能靠自律**

分類與標籤走白名單（`taxonomy.ts`），用 zod 在建置時驗證。打錯字 → build 直接失敗 → 你當場就知道。這是唯一能撐到 300 篇還維持整齊的方法。
→ 詳見 [03-內容模型與撰寫規範](./03-內容模型與撰寫規範.md#分類與標籤白名單)

## 這個專案為什麼長這樣

如果未來的你（或別人）想改動架構，先讀懂這三條推論鏈：

**「兩種使用者共用同一塊平板螢幕」→ 幾乎所有 UI 決策**
孩子看圖、說書人看字，但只有一塊螢幕。所以圖片必須佔絕大部分畫面、文字要小但清楚、文字要能一鍵完全隱藏、翻頁要單手可操作。這不是美感偏好，是物理限制推導出來的。

**「主力是手持平板/手機」→ 觸控優先 + PWA + iOS 踩雷清單**
沒有鍵盤、沒有簡報筆、沒有投影機。而且 iPhone Safari **不支援元素全螢幕 API**，唯一去掉瀏覽器介面的方法是「加入主畫面」的 PWA standalone 模式 — 這讓 PWA 從「加分項」變成「必要功能」。

**「300 篇以上」→ 資產路徑抽象 + 白名單 + 按需快取**
規模改變了每一個技術選擇。1 GB 上限、20,000 檔限制、全站預快取會塞爆手機、自由標籤會失控 — 這些在 30 篇時都不是問題，在 300 篇時全部同時爆炸。所以要在還沒痛的時候先埋好退路。
